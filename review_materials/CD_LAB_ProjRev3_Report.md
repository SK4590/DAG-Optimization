## 2. Problem Statement & Scope

Standard Three-Address Code (TAC) generated by compiler frontends contains substantial local and global inefficiencies. While local DAG optimization effectively eliminates Common Subexpressions (CSE), evaluates static constants, and folds algebraic identities within a single straight-line basic block, it is fundamentally bounded by basic block boundaries. When programs include conditional branches, loops, and jumps, local analysis cannot determine whether a temporary variable computed in one block is ever used in successor blocks. Consequently, compilers produce dead temporary assignments and unneeded memory allocations.

### Review 3 Technical Challenges Solved:
* **Basic Block Partitioning:** Automatically splitting TAC streams at entry points, jump targets, and branch instructions using standard Dragon Book Algorithm 8.4.
* **Control Flow Graph Construction:** Correctly constructing directed edges for sequential fallthrough, conditional True/False branches, and cyclic loop back-edges.
* **Multi-Block Local DAG Coordination:** Running Value Numbering and local transformations per block while strictly preserving entry labels and exit jumps.
* **Global Live Variable Analysis (LVA):** Computing iterative backward dataflow equations to fixed-point convergence to identify live ranges across loop boundaries.
* **Global Dead Code Elimination (DCE):** Iteratively purging dead temporary assignments across the CFG whose values are never consumed downstream.

## 5. Review 3 Technical Implementations Breakdown

### A. Dragon Book 3-Rule Leader Identification & Partitioning (Algorithm 8.4)
A basic block is a maximal sequence of consecutive Three-Address Code instructions in which control enters exclusively at the first instruction and leaves exclusively at the last instruction without branching except at the end. Our engine partitions raw instructions by identifying leaders using the classical three Dragon Book rules:
1. **Rule 1 (Entry):** The first Three-Address Code instruction in the intermediate code stream is always a leader.
2. **Rule 2 (Jump Target):** Any instruction that is the target of a conditional or unconditional jump (e.g., target label of `goto` or `if ... goto`) is a leader.
3. **Rule 3 (Post-Jump):** Any instruction that immediately follows a conditional or unconditional jump is a leader.

### B. Control Flow Graph (CFG) Construction & Edge Types
* **Sequential Fallthrough Edges:** Created between block $B_i$ and $B_{i+1}$ when $B_i$ does not terminate in an unconditional jump.
* **Conditional True Edges:** Created from conditional branch blocks to the block beginning with the destination target label (colored green in Graphviz).
* **Conditional False Edges:** Created from conditional branch blocks to the sequential fallthrough block $B_{i+1}$ taken when the branch condition is false (colored red).
* **Loop-Back Edges:** Detected when the destination block index is less than or equal to the source block index ($\text{targetId} \le \text{sourceId}$), representing iterative while/for cycles (dashed blue).

### C. Multi-Block Local DAG Optimization Pass
For every basic block $B$ in the CFG, the engine invokes a fresh local `DAGOptimizer`. Entry labels and exit jumps are isolated, while internal computational statements undergo local Value Numbering, commutative canonicalization, constant folding, and CSE. The reconstructed instructions replace the block contents, maintaining full semantic equivalence while reducing local operations.

### D. Global Live Variable Analysis (LVA)
Live Variable Analysis is a backward dataflow analysis that determines which variables may be read along some execution path starting from the exit of a basic block before being redefined. The dataflow equations are formulated as:
* **$\text{GEN}[B]$ (Upward Exposed Uses):** Variables used in block $B$ before any assignment/definition in $B$.
* **$\text{KILL}[B]$ (Definitions):** Variables assigned a new value (defined/overwritten) in block $B$.
* **$\text{OUT}[B]$:** $\bigcup_{S \in \text{succ}(B)} \text{IN}[S]$
* **$\text{IN}[B]$:** $\text{GEN}[B] \cup (\text{OUT}[B] \setminus \text{KILL}[B])$

### E. Global Dead Code Elimination (DCE)
Equipped with fixed-point $\text{OUT}[B]$ sets, the engine scans each block $B$ backwards from the last instruction to the first. If an instruction defines a compiler temporary (e.g., $t_k = \dots$) and $t_k$ is NOT present in the current live set, the instruction is recognized as dead code and deleted. As dead instructions are purged, the live sets update dynamically, enabling cascading elimination of dead subexpression chains across the entire CFG.

## 6. In-Depth Explanation of the LVA Report Columns

| Column Header | Formal Dataflow Definition | Operational Meaning & Compiler Impact |
| :--- | :--- | :--- |
| **`Block`** | $B_k \in \{B_0, \dots, B_{N-1}\}$ | The basic block identifier in topological order within the CFG. |
| **`GEN[B]`** | $\{ v \mid v \text{ is read in } B \text{ before def in } B \}$ | Identifies upward exposed variable uses that this block requires from preceding blocks. |
| **`KILL[B]`** | $\{ v \mid v \text{ is defined/assigned in } B \}$ | Identifies variables overwritten by this block. Any prior value arriving from predecessors dies here. |
| **`IN[B]`** | $\text{GEN}[B] \cup (\text{OUT}[B] \setminus \text{KILL}[B])$ | Variables that must contain valid, preserved values at the entry boundary of block $B$. |
| **`OUT[B]`** | $\bigcup_{S \in \text{succ}(B)} \text{IN}[S]$ | Variables that must remain valid upon leaving block $B$ because some successor path needs them. |

### Why Two LVA Reports Are Generated and How They Differ:
* **Report 1 (Initial LVA - Phase 2):** Calculated directly on the raw, unoptimized input CFG. It reflects all redundant temporaries and dead assignments present in the original code.
* **Report 2 (Post-Optimization LVA - Phase 4):** Calculated on the transformed CFG after local DAG optimization and Dead Code Elimination have been executed.

#### Concrete Demonstration on Benchmark 8 (`sample8_cfg_lva_dce.tac`):

| Block | Report 1: Initial `KILL[B]` | Report 2: Post-Optimization `KILL[B]` | Dataflow Difference & Transformation Explanation |
| :--- | :--- | :--- | :--- |
| **$B_0$ (Entry)** | `{t1, t2, tdead1, x, y}` | `{t1, x, y}` | Notice `t2` and `tdead1` are completely eradicated. The local DAG folded `t1 = 200`, while DCE purged dead variables `t2` and `tdead1`, shrinking $\text{KILL}[B_0]$. |
| **$B_1$ (Loop)** | `{t3, t4, t5, tdead2, x}` | `{t3, t5, x}` | Redundant temporary `t4` was folded into `t3` via local CSE, while unused dead variable `tdead2` was eliminated by backward DCE. |
| **$B_2$ (Exit)** | `{ans}` | `{ans}` | The final return statement remains intact, computing `ans` from the minimized live set `{t1, x}`. |
